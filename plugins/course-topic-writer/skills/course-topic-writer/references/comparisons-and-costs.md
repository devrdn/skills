# Comparisons and costs

- *Compare by properties, not by pluses and minuses.* A comparison table has criteria as rows (unit of data, how it is accessed, who works with it at once, latency, where data lives, capacity, what you pay for, typical use) and options as columns. A property is a limitation only for a particular task, so do not label it a minus, and never list a mere access method ("работает через API") as a drawback. Say so once next to the table.
- *Describe first, then constrain and price.* When options are compared in detail (storage classes, instance types, volume types), first a table of what each option is and when it is used, with an example of data or workload; then a table of limits and approximate prices.
- *Give real numbers for costs.* When a section is about cost (the request asks about cost, or the profile's section order has a cost part), give concrete prices for a named region with the date of the price list and a footnote to the official pricing page, plus a short worked calculation for a teaching scenario. State that prices change. Never estimate prices from memory.

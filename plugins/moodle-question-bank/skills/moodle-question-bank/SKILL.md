# Банк вопросов Moodle

У банка две задачи: проверить, что студент понял после чтения темы, и помочь ему запомнить тему, пока он отвечает. Каждый вопрос, каждый неверный вариант и каждое пояснение служит одной из этих задач. Вопрос, который просто трудный, длинный или про мелкое отступление, не служит ни одной.

Вопросы пишутся на языке материала (обычно на русском). Сообщение пользователя важнее правил скилла.

## Главные правила автора

Их автор поправляет чаще всего. Подробности - в `references/rules.md`, номер раздела в скобках.

1. _Основы первыми._ Каждому центральному термину темы - прямой вопрос ("Что такое бакет в Amazon S3?"); это примерно четверть вопросов типа 1 основного набора (2).
2. _Показывай кодом._ Политику, команду, конфигурацию, таблицу маршрутов, правила, URL клади в поле `code`, а не пересказывай словами (4).
3. _Грамотный русский._ Каждый вопрос и вариант звучит как фраза преподавателя вслух. Русских сокращений нет, английские сокращения терминов раскрыты в скобках при первом упоминании в вопросе (3).
4. _Не опирайся на главу._ Ни её персонажей, ни сквозного примера, ни её аналогий, ни её кода: новые ситуации и новый код (1).
5. _Форма не выдаёт ответ._ Варианты одной длины и одного построения, без пар противоположностей (5).
6. _Один факт - один раз в наборе_, включая строки соответствия; extra - того же уровня, на другие факты (11, 12).

## Файлы скилла

Пути - от папки скилла. Читай только то, что нужно на текущем шаге.

| Файл | Когда читать |
| --- | --- |
| `references/rules.md` | Всегда, перед тем как писать или править вопросы |
| `references/format.md` | Когда пишешь `bank.json` или сомневаешься в типе вопроса и XML |
| `references/essay.md` | Просят вопросы с открытым ответом, вопросы по Блуму или рубрику |
| `references/agents/<роль>.md` | Перед запуском субагента этой роли; передай ему файл как задание |
| `scripts/build_bank.py` | Собирает из `bank.json` XML, ключи в Markdown и версию без ответов для агентов |
| `scripts/check_bank.py` | Проверяет банк, считает вопросы и длины, запускает код, сравнивает ответы агентов с ключом |
| `scripts/edit_bank.py` | Правки по номерам: `show`, `apply --remove/--to-extra/--to-main`, `fill-run-results` |
| `scripts/import_xml.py` | Восстанавливает `bank.json` из выданных XML, если рабочий файл потерян |
| `scripts/build_essay.py` | Открытые вопросы: рубрика в Markdown, затем XML типа essay |

## Что нужно на входе

Из просьбы или из разговора:

1. _Материал._ Файл, вставленный текст или ссылка. Прочитай его целиком до начала работы. Если это глава на GitHub, бери текущую версию из репозитория: автор правит главы между просьбами.
2. _Номер темы_ `N`. Из просьбы или заголовка главы; спрашивай, только если его нет нигде.
3. _Курс._ Он задаёт корень категорий Moodle и язык вопросов с кодом (таблица "Курсы").
4. _Число вопросов по категориям, наборам и типам._ Например: "50 вопросов 1 типа, 15 второго, 4 на соединение; c: 8; u: 3; extra: 10 первого типа, 4 второго, 2 на соединение, c: 2, u: 1".

| Категория | Суффикс | Что в ней |
| --- | --- | --- |
| Основная | нет | Тип 1: один или несколько верных. Тип 2: пропуск. Соответствие |
| Что выведет программа | `c` | Около 80% ввода вывода (`output`), около 20% выбора исхода (`output_choice`) |
| Написать или исправить код | `u` | Только задачи CodeRunner |
| Открытый ответ | свой, например `an` | Вопросы на применение и анализ с рубрикой (`references/essay.md`) |
| Любая другая | свой, например `a` | Типы, которые назвал пользователь |

Числа по умолчанию:

- Если дано только общее число вопросов типа 1, примерно каждый девятый - с несколькими верными: round(всего / 9), не меньше одного при 6 и более вопросах, ни одного при меньшем числе (5 из 45, 6 из 50, 1 из 12, 0 из 4).
- В категории `c` примерно каждый пятый вопрос - `output_choice`; при числе вопросов меньше трёх их нет.
- Если своя категория смешивает два типа ("Gapfill + Matching") без разбивки, раздели примерно поровну и одной строкой назови разбивку в ответе.
- Если числа, нужного для сборки, нет ни в просьбе, ни в разговоре, спроси один раз и предложи своё значение.

## Номера и файлы

Номера идут по порядку. Внутри каждой категории и набора вопросы упорядочены по типу (single, multi, gap, match, output, output_choice, code) и пронумерованы с 01:

- Основной набор: `05_01`, `05_02`, ...; `05c_01`, ...; `05u_01`, ...
- Extra: `05*_01`, ...; `05c*_01`, ...; `05u*_01`, ...

Номер - всё содержимое `<name>` в Moodle: без заголовка и слов темы. Номера ставит скрипт сборки, вручную их не пишут.

Файлы: по XML на группу типов и по ключу в Markdown на набор (имена даёт скрипт):

- Основной набор: `L05_choice.xml`, `L05_gapfill.xml`, `L05_matching.xml`, `L05c_output.xml`, `L05u_code.xml`, `L05_questions.md`
- Extra: `L05Q_choice.xml`, `L05Q_gapfill.xml`, `L05Q_matching.xml`, `L05cQ_output.xml`, `L05uQ_code.xml`, `L05Q_questions.md`

Категории Moodle: `$course$/<Курс>/Лекция 5`, `.../Лекция 5 (c)`, `.../Лекция 5 (extra)`, `.../Лекция 5 (c, extra)`. Слово "Лекция" - поле `unit` в `bank.json`; если курс называет главу иначе ("Тема"), поменяй его. В ключе в Markdown только вопросы и ответы: без разделов, заметок для проверяющего и объяснений. Объяснения идут в `generalfeedback` в XML, студент видит их после ответа.

## Новый банк

1. _Прочитай материал и составь карту._ Выпиши разделы и для каждого - что стоит проверять: сначала центральные термины темы (`references/rules.md`, раздел 2), затем различия близких понятий, причины и следствия, выбор с компромиссами. Отметь, что не годится для вопросов: отступления, врезки NOTE и WARNING, сноски, даты, устаревающие числа. Для темы по программированию выпиши конструкции языка, изученные в этой и прошлых темах: вопросы с кодом используют только их.
2. _Распредели вопросы._ По разделам пропорционально их весу, а не с начала главы. Сначала вопросы на основные термины, затем на понимание и сценарии. Реши, что проверяет каждый тип, чтобы один факт проверялся один раз в категории и наборе. Основной набор и extra пиши одним пулом и потом раздели: extra - вопросы того же уровня на факты, которых нет в основном наборе. Везде, где вопрос про политику, команду, конфигурацию или URL, запланируй показать их кодом.
3. _Напиши `bank.json`_ в рабочей папке по `references/format.md` и `references/rules.md`. Пиши верный вариант первым: скрипт сам расставит порядок в XML и сдвинет букву ответа в ключе. `bank.json` остаётся в рабочей папке для будущих правок и не выдаётся, если не просят.
4. _Собери и проверь._
   ```bash
   python3 <папка скилла>/scripts/build_bank.py bank.json --out <папка выдачи>
   python3 <папка скилла>/scripts/check_bank.py bank.json --run-code
   ```
   Исправь каждую ошибку. Каждый ответ `output`, каждый исход `output_choice` и каждый тест CodeRunner должен пройти запуск; вопрос, код которого не удалось запустить, выдаётся только с оговоркой.
5. _Проверка агентами._ Собери версию без ответов и параллельно запусти трёх агентов, каждого с чистым контекстом:
   ```bash
   python3 <папка скилла>/scripts/build_bank.py bank.json --student student.md --key key.json
   ```
   - _Рецензент_: материал, оба ключа в Markdown и `references/rules.md`.
   - _Студент_: материал и `student.md`, без ключа; пишет `student_answers.json`.
   - _Детектор подсказок_: только `student.md`, без материала и ключа; пишет `leak_answers.json`.

   Затем сравни:
   ```bash
   python3 <папка скилла>/scripts/check_bank.py bank.json --compare key.json student_answers.json
   python3 <папка скилла>/scripts/check_bank.py bank.json --compare key.json leak_answers.json --leak
   ```
   Промах Студента значит: вопрос неоднозначен, ключ неверен или материал его не поддерживает. Разбери каждый промах и исправь вопрос или ключ.

   Попадание Детектора с подсказкой формы (длина, повтор слова из вопроса, пара противоположных вариантов, оговорка, грамматика) исправляй всегда, даже если Студент ответил верно: перестрой варианты так, чтобы подсказки не осталось. Ложная тревога - только попадание с `cue: "none"` или по знанию предмета.
6. _Пересобери, проверь и выдай._ Отправь XML и оба ключа. Ответ короткий: по каждому файлу диапазон номеров и число вопросов по типам. Одной строкой - что не удалось проверить. Отчёты агентов не пересказывай.

## Правки

Большинство следующих просьб - правки по номерам: "убери 05_06", "05_07 перенеси в extra", "05_56 - 05_59 убери", "поправь нумерацию", "переформулируй 03_12", "вставь политику прямо в вопрос", "напиши аббревиатуру полностью".

1. Загрузи текущий `bank.json`. Если его нет, восстанови из последних выданных XML через `scripts/import_xml.py` (с `--md` и выданным ключом, чтобы вернуть название темы) и скажи об этом одной строкой. XML не хранит настоящий вывод для `output_choice`, поэтому после импорта запусти `edit_bank.py bank.json fill-run-results`.
2. Сначала правки содержания (новая формулировка, код, раскрытые сокращения): найди каждый вопрос по его текущему номеру через `show`. Затем все переносы и удаления из сообщения - одним вызовом: `edit_bank.py bank.json apply --remove ... --to-extra ... --to-main ...`. Все номера, включая диапазоны вроде `05_56-05_59`, читаются по нумерации, которую видел пользователь, до любых изменений; отдельные вызовы читали бы следующие номера по уже перенумерованному банку. Скрипт печатает каждый затронутый вопрос с первыми словами, чтобы ошибка была видна. Если номер под сомнением, сначала `show`.
3. Перенесённый вопрос попадает в конец блока своего типа в целевом наборе. Остальные вопросы не трогай: их формулировки остаются как были.
4. Пересобери и проверь; номера идут без пропусков. Выдай каждый файл, содержимое которого изменилось (перенумерация тоже меняет файл), и оба ключа, с новыми диапазонами. Импорт в Moodle добавляет вопросы, а не заменяет их, поэтому если номера сдвинулись, одной строкой скажи, что старые вопросы затронутых категорий нужно удалить перед импортом новых файлов.
5. Если номер в просьбе записан неверно или двусмысленно ("05_04*"), выбери самое вероятное прочтение, выполни его и одной строкой назови прочтение, чтобы пользователь мог поправить.

Просьба исправить один вопрос не разрешает переписывать соседние. Если пользователь убирает вопросы как "слишком сложно", "не нужно", "повтор" или "звучит неграмотно", считай это настройкой для всей дальнейшей работы в разговоре: такие вопросы больше не пиши, как и случаи из раздела 12 `references/rules.md`.

## Курсы

| Курс | Корень категорий | Язык `c` и `u` | Тип CodeRunner |
| --- | --- | --- | --- |
| Cloud Computing | `$course$/Cloud Computing` | Python | `python3` |
| Веб-разработка (PHP) | `$course$/Web Development` | PHP | `php` |
| Основы программирования (C++) | `$course$/Programming Foundations` | C++ | `cpp_program` со stdin, пока не пройдены функции, затем `cpp_function` |

Для другого курса корень берётся из названия курса, а язык из материала; спрашивай, только если в материале нет кода, а пользователь просит `c` или `u`. В одном банке `c` и `u` на одном языке. Общее правило за строкой C++: задача CodeRunner требует только изученного, поэтому до функций это целая программа, которая читает stdin. Код для показа в вопросах с выбором (`references/rules.md`, раздел 4) не ограничен языком курса: в Cloud Computing политики IAM и бакетов показываются как `json`, команды CLI как `bash`.

## Агенты

| Роль | Файл | Модель | Получает | Возвращает |
| --- | --- | --- | --- | --- |
| Рецензент | `references/agents/reviewer.md` | `opus` | Материал, оба ключа, `references/rules.md` | Замечания по номерам |
| Студент | `references/agents/student.md` | `sonnet` | Материал, `student.md` | `student_answers.json` |
| Детектор подсказок | `references/agents/leak-detector.md` | `haiku` | Только `student.md` | `leak_answers.json` |

Субагент получает файл своей роли и полные пути к файлам из "Получает", а не пересказ разговора. Если установлен плагин `moodle-question-bank`, запускай роли агентами плагина: `moodle-question-bank:reviewer`, `moodle-question-bank:student`, `moodle-question-bank:leak-detector`. Вопросы пишет и исправляет основная сессия: один банк, один автор.

Если субагентов запустить нельзя (например, ты сам субагент), сделай три прохода сам, отдельными чтениями, каждый со своим файлом роли, и одной строкой скажи об этом в ответе: автор, который проверяет свои вопросы, находит меньше, особенно в роли Детектора. Часть пробела закрывает `check_bank.py`: длины вариантов и верный вариант, который один повторяет слова вопроса.
